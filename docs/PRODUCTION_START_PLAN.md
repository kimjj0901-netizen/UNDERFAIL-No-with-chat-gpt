## 2. 워크북에서 확인되는 제작 기준

### 사용자 작성 내용에서 확인한 방향

1. **작품:** UNDERFAIL / 《언더페일》.
2. **배경:** 풍화양상 고등학교. 현실 학교와 완전히 같지 않은 판타지적 학교이며, 교실마다 고유한 특징이 있고 교사는 성향에 맞는 능력을 갖는다.
3. **주인공:** 플레이어가 이름과 대사를 선택하는 방식은 Undertale의 진행 감각을 참고한다. 주인공이 지키려는 핵심은 특정 예체능 한 분야보다 자유롭게 자신의 진로를 선택할 권리다.
4. **입학 배경:** 각종 시험 점수와 생활기록을 바탕으로 풍화양상 고등학교에 배정된다.
5. **전투의 의미:** 학생과 교직원이 목표를 두고 벌이는 경쟁·대립이다. 주인공은 꿈을 가로막는 학교 구조, 학생회·선도부·교사 등과 대립할 수 있다.
6. **전투 형식:** 공격, 행동/ACT, 아이템, 자비/비폭력 해결, 상대 턴의 탄막 회피 등 Undertale의 전투 흐름을 적극 참고한다.
7. **장비:** 이전 학생이 남긴 물품을 장비로 활용한다. 예체능 관련 물품이 중심이며, 장비에 따라 능력치와 공격 방식이 달라질 수 있다.
8. **아이템:** 회복 외에도 전투 패턴 완화, 특정 인물과의 관계, 작은 이스터에그, 이전 사건의 증거 등의 기능을 가질 수 있다.
9. **관계:** 단일 호감도보다 인물마다 서로 다른 관계 요소를 쓰는 방향을 채택했다. 루트별 도움 방식은 달라질 수 있다.
10. **루트:** 기본 루트와 불살 루트는 채택 상태다. 몰살 관련 최종 명칭·조건·제압 결과는 보류 항목을 존중한다.
11. **정서:** 모든 인물이 단순히 나쁜 사람인 것은 아니라는 관점이 중요하다. 지나치게 원작에서 벗어나거나 회수하기 어려운 복선을 무리하게 늘리지 않는다.

## 4. 기술 스택 제안

### 기본 제안 — Phaser 4 + TypeScript + Vite

**상태: Proposal / 승인 전**

- **Phaser 4:** 2D 방 탐험, 스프라이트, 카메라, 애니메이션, 충돌, 장면 전환 및 전투 화면을 담당한다.
- **TypeScript:** 대화 이벤트·인물 상태·아이템·전투 상태의 데이터 구조를 명확하게 관리한다.
- **Vite:** 개발 서버와 웹 빌드를 담당한다.
- **HTML/CSS:** 타이틀 화면, 옵션, 외부 UI가 게임 캔버스와 분리되어야 할 때만 사용한다.
- **React/Three.js:** 이 프로젝트에는 기본 채택하지 않는다. 별개 3D 프로젝트의 기술 스택을 가져오지 않는다.

공식 Phaser 문서에는 Phaser 4.2.1 배포본과 TypeScript 지원이 안내되어 있다. 공식 프로젝트 생성 도구는 Vite를 선택할 수 있고, 처음 시작하는 사용자는 Web Bundler와 Vite 조합을 선택하도록 안내한다.

- Phaser 4.2.1: https://phaser.io/download/release/v4.2.1
- 공식 프로젝트 생성 도구: https://github.com/phaserjs/create-game
- 설치 안내: https://www.phaser.io/oss/docs/phaser/getting-started/installation
- Scene 개념: https://www.phaser.io/oss/docs/phaser/concepts/scenes

### 왜 이 조합인가

《언더페일》에서 우선 필요한 기술 문제는 3D 렌더링이 아니라 다음 네 가지다.

1. 타일/방 기반의 2D 이동과 충돌
2. 조사·대화·아이템 이벤트의 조건 처리
3. 탐험 화면과 전투 화면의 전환
4. 탄막 회피와 보스별 고유 전투 규칙

Phaser는 이 2D 게임 루프를 직접 다루는 엔진이고, TypeScript는 캐릭터와 이벤트의 조건이 늘어날 때 실수를 줄이는 데 유리하다. Vite는 프로젝트 실행·새로고침·웹 빌드에 사용한다.

**다른 선택지:** Phaser Agent/Phaser AE 같은 AI 중심 도구도 존재하지만, 이번 기본안은 Copilot이 직접 읽고 수정할 수 있는 일반 소스 코드 프로젝트를 우선한다. 엔진은 승인 전까지 최종 정사가 아니다.

## 5. 첫 번째 목표: Vertical Slice

처음부터 전체 스토리나 모든 지역을 구현하지 않는다. 게임의 핵심 재미가 작동하는 짧은 구간 하나를 완성한다.

### 첫 플레이 가능 구간

**이름 입력 → 오프닝 → 교육복지실 탐험 → 도미토리엘과 대화 → 첫 전투 → 비폭력 해결 → 다음 공간으로 이동**

여기서 구현할 기능은 다음과 같다.

| 기능 | 최소 통과 기준 |
|---|---|
| 게임 시작 | 브라우저에서 타이틀과 새 게임 시작이 표시된다. |
| 이름 입력 | 플레이어가 주인공 이름을 입력하거나 선택할 수 있다. |
| 방 이동 | 주인공이 2D 공간을 걷고 벽·장애물과 충돌한다. |
| 조사 | 오브젝트를 조사하면 대상에 맞는 문구가 나온다. |
| NPC 상호작용 | 도미토리엘과 대화하고 선택지에 따라 다른 반응을 얻는다. |
| 대화 UI | 텍스트 상자, 이름표, 선택지, 확인/취소 입력이 작동한다. |
| 전투 진입 | 탐험 화면에서 전투 화면으로 자연스럽게 전환된다. |
| 전투 메뉴 | 공격·행동·아이템·자비에 해당하는 메뉴를 표시한다. |
| 상대 턴 | 플레이어가 제한된 전투 영역 안에서 탄막을 피한다. |
| ACT 해결 | 도미토리엘의 걱정과 보호 의도를 이해하고 자신의 진로 선택 의지를 반복해서 표현한다. |
| 전투 종료 | 공격하지 않고 일정 조건을 충족하면 도미토리엘이 길을 열어 준다. |
| 상태 유지 | 장면이 바뀌어도 이름·아이템·이벤트 플래그가 사라지지 않는다. |

이 구간이 완성되면 같은 구조를 파프리카, SANZ, 체임버쌤 등의 전투에 재사용할 수 있는지 검증한다.

## 6. 권장 아키텍처 초안

**모든 대화와 방을 한 파일에 몰아넣지 않는다.** 장면 실행 로직과 콘텐츠 데이터를 분리한다.

```text
/
├─ CREATIVE_DECISION_WORKBOOK.md
├─ README.md
├─ docs/
│  ├─ CANON_BASELINE.md
│  ├─ GAME_DESIGN.md
│  ├─ BATTLE_SYSTEM.md
│  ├─ EVENT_AND_FLAG_SCHEMA.md
│  ├─ TECH_ARCHITECTURE.md
│  └─ IMPLEMENTATION_ROADMAP.md
├─ public/
│  └─ assets/
│     ├─ characters/
│     ├─ tilesets/
│     ├─ backgrounds/
│     ├─ portraits/
│     └─ audio/
└─ src/
   ├─ main.ts
   ├─ game/
   │  ├─ config/
   │  ├─ scenes/
   │  ├─ entities/
   │  ├─ systems/
   │  ├─ ui/
   │  └─ data/
   └─ styles/
```

이 구조는 제안이다. 실제 프로젝트 생성 후 템플릿과 충돌하는 부분이 있으면 Copilot이 먼저 설명하고 수정해야 한다.

### 주요 시스템 경계

- **Scene:** Boot, Title, Exploration, Battle 등 화면/장면 전환.
- **Room data:** 방 크기, 타일, 충돌 구역, 출구, 조사 오브젝트, NPC 위치.
- **Dialogue data:** 화자, 문장 묶음, 선택지, 출력 조건.
- **Event system:** 플레이어 행동, 아이템, 이전 이벤트 플래그에 따른 반응.
- **Battle system:** 턴 상태, 메뉴 선택, 적의 행동, 회피 영역, ACT 반응, 종료 조건.
- **Game state:** 이름, HP, 인벤토리, 장비, 관계 플래그, 루트 플래그, 방문 기록.
- **Save system:** 저장 데이터 형식은 구현하되, 저장/재시작을 캐릭터가 인식하는 세계관 설정은 별도 승인 전까지 넣지 않는다.

## 8. Copilot 작업 규칙

Copilot에게 한 번에 전체 게임을 무작정 구현하라고 하지 않는다. 하나의 Milestone 단위로 맡기되, 관련 문서 3~5개만 컨텍스트로 제공한다.

Copilot은 매 작업마다 다음 순서를 지킨다.

1. 현재 브랜치와 파일 구조 확인.
2. 지정된 문서와 기존 코드를 먼저 읽는다.
3. 구현하려는 변경과 영향 파일을 짧게 제시한다.
4. 기존 기능을 보존하며 구현한다.
5. TypeScript 검사·빌드·가능한 테스트를 실행한다.
6. 오류가 있으면 수정하고 다시 검증한다.
7. 변경 파일, 실행 결과, 미완성·위험 요소를 보고한다.
8. 사용자 승인 없이 Canon이나 보류 설정을 바꾸지 않는다.

### 첫 Copilot 작업에 지정할 파일

프로젝트 기반을 만든 뒤에는 다음 정도만 전달한다.

```text
#file: CREATIVE_DECISION_WORKBOOK.md
#file: docs/CANON_BASELINE.md
#file: docs/TECH_ARCHITECTURE.md
#file: docs/IMPLEMENTATION_ROADMAP.md
```

아직 파일이 생성되지 않았다면 존재한다고 가정하지 말고 먼저 생성 계획을 보고하도록 한다.

## 9. 첫 번째 구현 요청의 완료 조건

첫 구현 작업은 '게임 전체 완성'이 아니라 다음을 보여주는 것이다.

- 새 게임을 눌러 실제 게임 화면에 들어갈 수 있다.
- 플레이어 캐릭터가 방 안에서 움직인다.
- 조사 가능한 물건이 최소 2개 있다.
- 대화할 수 있는 NPC가 최소 1명 있다.
- 대화 선택에 따라 반응이 달라진다.
- 전투 화면으로 진입하고 다시 탐험 화면으로 돌아올 수 있다.
- 개발 서버 실행과 프로덕션 빌드가 성공한다.
- 새로고침 또는 장면 전환 뒤 상태가 의도하지 않게 초기화되지 않는다.
