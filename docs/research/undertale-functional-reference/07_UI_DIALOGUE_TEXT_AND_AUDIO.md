# 07 — UI, 대화, 텍스트, 음향 피드백

## 1. 화면의 레이어

전투 화면은 적과 SOUL, 공격 보드, 상태표시, 선택 메뉴가 화면 안에서 명확한 층을 이룬다.

~~~text
┌──────────────────────────────────────────┐
│                                          │
│             ENEMY / SCENE                │
│                                          │
│               ENEMY                      │
│                                          │
│             ┌──────────────┐             │
│             │              │             │
│             │    SOUL      │             │
│             │              │             │
│             └──────────────┘             │
│                                          │
├──────────────────────────────────────────┤
│ NAME  LV  HP / MAX HP                     │
│                                          │
│ [FIGHT] [ACT] [ITEM] [MERCY]              │
└──────────────────────────────────────────┘
~~~

위 도식은 기능 배치를 설명하는 재구성이다. 원작 이미지 그대로가 아니다.

## 2. 메뉴의 일관된 규칙

메뉴는 장식용 버튼이 아니라 게임의 명령 진입점이다. 메뉴의 선택 상태, 이동 방향, Confirm, Cancel은 입력 추상화와 연결되어야 한다.

[UNDERFAIL 제안]
- 키보드 커서는 선명하게 표현한다.
- 선택 항목은 색·아이콘·프레임·텍스트 중 둘 이상으로 구분한다.
- 사용 불가 항목은 회색 처리만 하지 말고 사용 불가 이유를 제공한다.
- 마우스를 추가 지원하더라도 키보드 조작을 완전하게 유지한다.
- 메뉴에서 마우스 포인터와 키보드 커서가 서로 다른 항목을 가리키지 않게 한다.

## 3. 텍스트 박스

Undertale은 이야기의 많은 부분을 대화와 짧은 텍스트 반응으로 전달한다. 대화는 탐험과 전투의 일부이며, 플레이어가 Confirm을 눌러 다음 문장으로 진행하는 리듬을 만든다.

[검증 한계] 텍스트 타자 효과의 정확한 프레임 속도, Cancel 길게 누르기, 특정 대화의 스킵 규칙 등은 직접 실행 테스트를 하지 않았다. 관련 기능을 구현할 때는 실제 PC판에서 확인해야 한다.

## 4. 대화 상태 구조

~~~ts
interface DialogueRuntime {
  dialogueId: string;
  pageIndex: number;
  characterId?: string;
  text: string;
  isTyping: boolean;
  waitingForConfirm: boolean;
  canCancel: boolean;
  canAdvance: boolean;
}
~~~

여기서 중요한 것은 화면에 표시하는 문자열과 대화 진행 상태를 분리하는 것이다.

- 대사 출력 중 Confirm을 누른 경우: 현재 페이지를 즉시 완성할 것인지, 다음 페이지로 넘어갈 것인지 규칙이 필요하다.
- 페이지 출력이 완료된 경우: Confirm으로 다음 페이지를 진행한다.
- 선택지가 있는 경우: 방향키로 선택지 커서를 움직이고 Confirm으로 확정한다.
- 대화가 열렸을 때: 탐험 이동 입력을 잠근다.
- 대화가 닫힐 때: 잠금과 키 상태를 초기화한다.

## 5. 말풍선과 캐릭터 표현

[설계 해석] 캐릭터가 매 프레임 복잡하게 움직일 필요는 없다. 작은 스프라이트/표정 변화, 대사, 중요한 순간의 포즈 변화가 결합되면 감정 전달이 가능하다.

~~~text
IDLE
  ↓
DIALOGUE_PAGE
  ↓
FACE / POSE CHANGE
  ↓
PAUSE
  ↓
IMPORTANT REACTION
~~~

이 흐름은 UNDERFAIL의 캐릭터 애니메이션을 설계할 때 사용할 수 있는 일반 원리다. 원작의 표정 스프라이트를 복제하지 않는다.

## 6. 텍스트 정보의 양

- 한 화면에서 한 번에 읽을 텍스트 길이를 조절한다.
- 화자 이름과 대사 내용을 분리한다.
- 중요한 선택지는 한 화면에서 모두 볼 수 있게 한다.
- 캐릭터의 성격을 설명하는 긴 문단보다 짧은 반응과 플레이어의 행동 결과로 표현한다.
- 조사 대상의 문구는 인물의 현재 상태를 반영한다.

## 7. 효과음과 음악 타이밍

Toby Fox가 전투 설계에 대해 설명한 글은 패턴의 짧은 단위와 조우 다양성을 강조한다. 게임의 감각을 만드는 데는 시각 신호뿐 아니라 소리의 시작/정지와 타이밍도 중요하다.

[UNDERFAIL 제안]
- Confirm 소리, 메뉴 커서 이동, 아이템 사용, 피격, 해결 성공의 음향을 별도 이벤트로 둔다.
- BGM은 지역/캐릭터/전투 상태와 분리해 상태 변화 이벤트로 제어한다.
- 중요한 정적은 음악을 크게 만드는 것보다 더 강한 연출이 될 수 있다.
- 게임 시작 전 오디오 재생이 차단되더라도 플레이가 멈추지 않게 한다.
- 효과음은 사용자 설정으로 전체 음량과 개별 음량을 조절할 수 있게 설계한다.

## 8. 화면 분위기와 전투 UI

이전 답변에서 검은 공간, 흰색 경계, 흰색 텍스트, 선택 강조색을 Undertale UI의 시각적 특징으로 정리했다. 이는 화면 관찰에 기반한 시각 분석이며 공식 디자인 시스템 문서는 아니다.

UNDERFAIL에 적용한다면, 학교 세계의 독자적인 서체/색/테두리/텍스트 장식으로 바꾸어야 한다. 원작의 전투 메뉴 아트와 글꼴을 그대로 사용하지 않는다.

## 9. 현재 프로젝트 문서와 차이

[기존 프로젝트 사실] docs/TECH_ARCHITECTURE.md는 대화 중 이동 잠금, 키보드로 대사 진행/선택지 이동/닫기 기능을 제안하고 있다. docs/design/OPENING_VISUAL_DIRECTION.md는 타이틀 및 컷신 등에 Enter/Space 또는 클릭 입력이 섞인 초기 방향을 기록한다.

이는 현재 프로젝트 입력 규칙이 문서마다 완전히 통일되어 있지 않을 수 있음을 뜻한다. UI 재설계 전에 입력 체계를 먼저 정리해야 한다.

## 10. 접근성 체크

- 텍스트 대비가 충분한지.
- 작은 화면에서도 텍스트가 읽히는지.
- 색상만으로 선택/위험 상태를 구분하지 않는지.
- 반복 점멸과 강한 화면 흔들림을 피하는지.
- Confirm을 연속으로 눌렀을 때 원치 않는 선택이 중복되지 않는지.
- 키보드만으로 모든 핵심 화면을 조작할 수 있는지.
- 마우스를 지원하면 포커스 이동과 키보드 동작이 충돌하지 않는지.

현재 이 항목들의 브라우저 실기 검수는 수행하지 않았다.
