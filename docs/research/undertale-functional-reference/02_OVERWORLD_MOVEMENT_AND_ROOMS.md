# 02 — 오버월드 이동, 충돌, 방 구조, 카메라

## 1. 방 단위 탐험의 구조

[원작 게임 기능 — 2차 확인] Undertale은 플레이어가 방(room)을 이동하며 탐험하는 구조로 이해하는 것이 적합하다. 각 방은 이동 공간이면서도 작은 장면, 대화, 퍼즐, 조우를 담는 단위다.

[설계 해석] 한 방 안에 모든 이야기를 몰아넣는 대신, 방 진입 → 공간 파악 → 등장인물 발견 → 사물 조사 → 퍼즐/대화 → 다음 방으로 연결하는 식으로 플레이 템포를 나눌 수 있다.

~~~text
ROOM_A
  ├─ entrance
  ├─ NPC
  ├─ inspectable objects
  ├─ puzzle / event trigger
  └─ exit → ROOM_B
~~~

## 2. 이동의 체감

직전 답변에서는 Undertale의 오버월드 이동을 4방향 이동, 즉시 정지, 가속 곡선 없음, 달리기 버튼 없음, 대각선 이동 없음으로 설명했다.

이 중 이번에 확인된 공개 2차 자료의 일부 설명은 그러한 조작을 보고하고 있지만, 이번 세션에는 PC 원본 게임을 직접 실행해 프레임별로 측정하지 않았다. 따라서 아래 항목은 모두 [직접 관찰 필요]다.

- 방향키 이동이 4방향만 가능한가.
- 두 방향키를 동시에 누를 때 대각선 보정이 있는가.
- 키를 놓는 즉시 멈추는가.
- 가속/감속이 있는가.
- 별도의 달리기 키가 있는가.
- 충돌 전후 이동 속도가 달라지는가.
- 대화 직전/직후 입력 버퍼가 유지되는가.

UNDERFAIL의 최종 이동감은 실제 테스트로 확인하기 전까지 이론만으로 고정하지 않는다.

## 3. 충돌 처리 모델

[설계 해석] Undertale의 탐험 공간을 재현하려는 경우 물리 시뮬레이션 자체를 복잡하게 만드는 것보다, 충돌 가능 영역과 스크립트 이벤트 영역을 분리해 관리하는 편이 개발 효율에 도움이 된다.

~~~ts
interface RoomCollision {
  id: string;
  x: number;
  y: number;
  width: number;
  height: number;
  kind: "WALL" | "FURNITURE" | "WATER" | "SCRIPTED_BLOCK";
}

interface InteractionTarget {
  id: string;
  x: number;
  y: number;
  radius: number;
  actionId: string;
  facingRequired?: "UP" | "DOWN" | "LEFT" | "RIGHT";
}
~~~

물체와의 일반 충돌, 상호작용 범위, 특정 이벤트에 따른 강제 이동/장면 전환은 서로 다른 데이터로 둔다.

예를 들어 다리가 무너지는 장면을 일반 물리로 처리할 필요는 없다. 트리거 구역 진입 → 짧은 연출 → 위치 이동/장면 전환이라는 스크립트로 설계할 수 있다.

## 4. 카메라

[검증 한계] Undertale의 모든 카메라 동작을 하나의 고정 규칙으로 요약할 수는 없다. 일반적으로 방의 크기와 장면에 맞춰 화면이 구성되며, 넓은 공간에서는 화면 이동이 필요할 수 있다. 특정 전투의 Bullet Board 이동/확대/축소와 오버월드 카메라를 같은 시스템으로 혼동하지 않는다.

UNDERFAIL에서는 다음의 경계를 분리할 것을 제안한다.

- Room camera: 현재 방의 화면 경계와 스크롤.
- Cutscene camera: 특정 장면을 강조하는 일시적인 프레이밍.
- Battle board transform: 적 턴의 전투 영역 크기와 위치.
- Screen transition: 페이드, 컷, 짧은 정지, 색/명도 변화.

## 5. 화면 비율과 640×480

이전 답변은 Undertale의 640×480을 기본 논리 해상도인 것처럼 사용했다. 이 표현은 수정이 필요하다.

[원작 자료 — 2차 확인] Undertale Wiki의 파일/스크린샷 안내에는 창 모드에서 게임이 보이는 크기를 640×480으로 취급하므로 스크린샷도 그 크기에 맞추라는 편집 기준이 있다. 이는 스크린샷의 표준 표현 크기라는 증거다. 내부 엔진 논리 해상도·모든 플랫폼 렌더링·모든 장면의 좌표계를 완전히 증명하는 문서는 아니다.

따라서 640×480을 게임 내부의 절대 불변 해상도라고 선언하지 않는다. 상세 스크린샷 기준은 출처 파일에서 확인한다.

## 6. UNDERFAIL 현재 화면과 충돌

[기존 프로젝트 사실] docs/TECH_ARCHITECTURE.md에는 현재 논리 해상도 960×540, Phaser.Scale.FIT, 중앙 정렬이 기록되어 있다. 이는 16:9 비율이다.

Undertale 스크린샷 기준으로 소개된 640×480은 4:3 비율이다. 비율을 그대로 바꾸면 다음이 달라질 수 있다.

- 방의 가로/세로 배치.
- 캐릭터 크기와 화면 내 위치.
- 텍스트 박스 폭.
- 전투 영역과 명령 메뉴 비율.
- 현재 제작 SVG의 화면 구성.
- 작은 브라우저 창에서의 축소 정도.

[UNDERFAIL 제안] 현재 해상도를 바로 교체하지 말고, 4:3 콘텐츠 영역을 임시로 별도 구성해 960×540 안에서 비교하거나, 별도 테스트 브랜치에서 4:3 화면을 실험한다. 결과를 실제로 비교한 뒤 사용자 승인으로 결정한다.

## 7. Room 데이터 구조 제안

~~~ts
interface RoomDefinition {
  id: string;
  logicalWidth: number;
  logicalHeight: number;
  backgroundAsset: string;
  collision: RoomCollision[];
  interactions: InteractionTarget[];
  exits: {
    id: string;
    targetRoomId: string;
    spawnX: number;
    spawnY: number;
    transition: "CUT" | "FADE";
  }[];
  encounterTriggers: {
    id: string;
    encounterId: string;
    x: number;
    y: number;
    width: number;
    height: number;
    conditionFlags?: string[];
  }[];
}
~~~

이 인터페이스는 구현 명령이 아니라 기획용 모델이다. 기존 Scene 코드에 바로 복사하기 전에 현재 Phaser 4.2.1 코드와 GameSession 경계를 확인한다.

## 8. 방 한 개의 연출 흐름

~~~text
방 진입
  ↓
입구/시선/배경 소품을 통해 방을 읽음
  ↓
NPC 또는 조사 대상 발견
  ↓
Confirm / Interact
  ↓
대화/조사 결과
  ↓
플래그 또는 관계 변화
  ↓
새 대사/퍼즐/출구 조건 확인
  ↓
다음 방
~~~

## 9. UNDERFAIL 적용 시 중요한 점

- 교육복지실과 복도는 서로 다른 방이어도 인접한 공간으로 느껴져야 한다.
- 문이나 출구는 현재 스토리 상태에 따라 이동 가능 여부가 달라질 수 있다.
- NPC의 대화가 끝났다고 해서 자동으로 다른 방으로 이동시키지 않는다.
- 전투 중에는 오버월드 이동 입력이 잠겨야 한다.
- 조사 범위와 벽/가구 충돌 범위는 서로 별도로 검증한다.
- 카메라 움직임은 캐릭터 이동보다 앞서지 않게 하고, 장면 연출 때만 예외적으로 바꾼다.

## 10. 직접 플레이 검증 계획

1. 같은 방을 4방향 각각 이동한다.
2. 벽·가구·모서리에서 충돌을 확인한다.
3. 방향키 두 개를 동시에 누른다.
4. 이동 중 대화/조사 입력을 누른다.
5. 대화 중 이동키를 누른다.
6. 방 경계 근처에서 화면 스크롤을 확인한다.
7. 출구 전환 중 방향키를 계속 누른다.
8. 해상도/창 크기 변경 시 화면 크기와 텍스트 가독성을 확인한다.

직접 플레이는 이 자료집 작성 중 수행하지 않았으므로 위 항목은 모두 미실행 상태다.
